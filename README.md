# DDO Wiki Search

A Django + SQLite web app that mirrors item pages from the Dungeons & Dragons
Online wiki (`https://ddowiki.com`) and provides a search UI with base filters
(name / item type / minimum level) plus enhancement filters (multi-row,
bidirectionally-scoped dropdowns, optional upgrade-tier inclusion, and
minimum-value filters like "+4 or better").

The system is designed around one core idea: **the wiki is only contacted
rarely.** Raw wikitext is captured to a local snapshot, wiki template renders
are cached locally, and enhancement rules compose some display text locally.
Everything else is offline and replayable.

---

## Why the wiki is hard to talk to (the starting constraint)

Everything about this app's shape follows from two facts about ddowiki:

1. **It sits behind AWS WAF.** A plain HTTP request returns an HTTP 202
   challenge page, not data. We must first solve a JS challenge in a headless
   Chromium browser to obtain an `aws-waf-token` cookie, then reuse that token
   on subsequent requests (it expires and must be re-solved).
2. **The "Enchantments" list on an item page is partly generated by wiki
   templates, not written out in the page's wikitext.** For example the page
   contains `{{Enhancement bonus|i|3}}`, and the wiki's *template engine*
   renders that to the human text "+3 Enhancement Bonus" plus "Spellcasting
   Implement +9". To get the display text you must ask the wiki's
   `expandtemplates` API to render the call.

Both facts push toward the same conclusion: **never touch the wiki unless you
have to, and cache what you do fetch.**

---

## Architecture

Four layers, separated so that wiki access is isolated and replayable:

```
ddowiki (WAF-protected)
   │  api_request()  ── solves AWS WAF token, paces requests
   ▼
┌──────────────────────────────────────────────────────────────┐
│ 1. CRAWL / IMPORT  catalog/management/commands/import_wiki.py │
│    Two symmetric, mutually exclusive modes:                   │
│    • --snapshot   → writes RAW wikitext to wiki_snapshot/     │
│    • --load-snapshot → reads snapshot, parses, writes the DB  │
│    Plus --page/--full/--limit/--reset-sync for live crawling. │
└──────────────────────────────────────────────────────────────┘
   │ snapshot (raw wikitext)          │
   ▼                                 ▼
┌───────────────────────┐   ┌─────────────────────────────────┐
│ 2. RENDER CACHE        │   │ 3. PARSE                        │
│    render_enhancements │   │    parse_item / parse_enhance-  │
│    → wiki_snapshot/    │   │    ments (import_wiki.py)        │
│      renders/*.json    │   │    enhancement_rules.py (data-  │
│    (wiki expandtemplates│   │    driven, admin-editable)       │
│    once per distinct   │   │    enhancement_renders.py        │
│    template call, incl.│   │    enhancement_values.py         │
│    raw_html for local  │   │                                  │
│    re-extraction)      │   │                                  │
└───────────────────────┘   └───────────────┬──────────────────┘
                                             ▼
                                      Item / ItemEnhancement
                                      (SQLite: db.sqlite3)
                                             ▼
┌──────────────────────────────────────────────────────────────┐
│ 4. SEARCH UI  views.py, services.py, item_search.html, .js    │
│    Pure server-side filtering + AJAX dropdown options          │
└──────────────────────────────────────────────────────────────┘
```

Only layers 1 and 2 contact the wiki, and only for things not already on disk.
Layers 3 and 4 are fully offline.

### Why the data lives on disk (not in the DB)

The snapshot pages and the render files are stored under `wiki_snapshot/` as
plain JSON — **deliberately not** in SQLite. Rationale:

- The DB (`db.sqlite3`) is disposable. If a parser change makes re-parsing
  necessary, wiping the DB and rebuilding is a one-line command. That only
  works because the wiki-derived data survives the wipe.
- A full wiki crawl takes ~5-6 minutes; a full render pass takes longer. Losing
  either to a DB wipe would be a real cost.
- The snapshot stores **raw wikitext**, not parsed rows, because parsing rules
  keep evolving. Raw text is the ground truth you can re-interpret forever;
  parsed rows are an interpretation.

## The structure of the wiki (what the importer reads)

### The `Item:` namespace and infobox

Item pages live in MediaWiki namespace 500 (`Item:`), one page per item. Each
page starts with an infobox template — for the items we import, `{{Named item|...}}`:

```
{{Named item|Weapon
  | name                     = Ethereal Bastard Sword
  | type                     = Bastard Sword
  | minlevel                 = 2
  | mythic                   = no
  | enhancements             =
* {{Enhancement bonus|w|1}}
* {{Ghost Touch}}
* {{Augment|Red}}
  | crafting                 =
  | description              = A subtle mist surrounds this weapon. ...
}}
```

The infobox carries the fields the search needs: `name` (display name), `type`
(slot/kind), `minlevel`, `mythic`, and the `enhancements` section. `parse_item`
pulls these with simple per-line regexes; `detect_kind` checks which infobox
template the page starts with (the `ITEM_INFOBLOXES` list — extend it to import
new kinds like Collectables).

### The `enhancements=` section

Each enhancement is a wiki template call on its own bullet line:

```
* {{Enhancement bonus|w|1}}        → "+1 Enhancement Bonus"
* {{SpellPower|Combustion|54}}     → "Combustion +54"
* {{Clicky|Nimbus of Light|1|50|50}} → "Nimbus of Light — 50 Charges (Recharged/Day:50)"
```

**Upgrade tiers** are a wiki convention nested under the base bullets:

```
* {{Enhancement bonus|i|7}}            base line
* {{CraftingEffects|Upgradeable Item}} base line
** Tier 1:                             tier header
*** Adds {{Spellpen|VI}}               tier-1 enhancement
*** Adds {{Acid Torrent}}              tier-1 enhancement
** Tier 2:                             tier header
*** Adds {{Blast|Acid}}                tier-2 enhancement
* {{SpellPower|Combustion|150}}        base line (resets the tier)
```

The parser tracks the "current tier" by reading the `*`/`**`/`***` indentation
between template calls: a base bullet resets it to None, a `** Tier N:` header
sets it, and following `***` lines are tagged with that tier number. This is
what powers the "Include upgrades" checkbox on the search page.

Some calls carry control parameters the wiki ignores for display:
`{{Spellpen|I|nocat=TRUE}}` — `nocat`/`cat`/`category` are stripped during
normalization and never treated as search values.

## How the import works

### Step 1 — Capture the snapshot (`import_wiki --snapshot`)

Crawls the `Item:` namespace via `list=allpages` (or incrementally via
`recentchanges`), fetching each page's wikitext through `prop=revisions`. Each
page is written to `wiki_snapshot/pages/<pageid>.json` and recorded in
`manifest.json` (`{pageid: {title, revision_id, file}}`). The manifest is
rewritten atomically after every batch, so an interrupted crawl resumes cleanly.

Incremental capture skips pages whose revision is unchanged against the
manifest. The recentchanges cursor is persisted in `wiki_sync_state.json`.

### Step 2 — Render enhancement templates (`render_enhancements`)

Scans the snapshot, collects every distinct enhancement template call, and asks
the wiki's `expandtemplates` API once per call. Each result is saved to
`wiki_snapshot/renders/<sha1>.json` with:

- `raw_html` — the wiki's exact HTML output (kept so parsing fixes can be
  re-applied locally later)
- `canonical_name`, `display_text`, `value`, `detail` — fields parsed from it

This is the slow step (one round-trip per call), so calls are sent **batched**:
the wiki accepts multiple templates in a single `text` blob (but rejects
newlines and very long URLs), so calls are joined with sentinel markers
(`@@K0@@ {{Call}} @@K1@@ {{Call}}`), capped at ~1900 URL characters, and split
apart again from the wiki's reply. If the wiki rejects a batch, it is shrunk in
half and retried.

**Rule-composed calls skip the wiki entirely.** When a template rule (below)
already produces the exact display text — SpellPower, Spelllore, Enhancement
bonus, HealingAmp — no wiki request is made at all.

### Step 3 — Load the snapshot (`import_wiki --load-snapshot`)

Reads `manifest.json` + page files, runs `parse_item`, and writes `Item` /
`Enhancement` / `ItemEnhancement` rows. Purely local — no wiki calls. Skips
items whose revision already matches the DB; `--force` reparses everything.

### The three offline sources of truth

| Data | Where | What it is |
|---|---|---|
| `wiki_snapshot/pages/` | disk | raw wikitext per page |
| `wiki_snapshot/renders/` | disk | wiki's rendered output per template call |
| `db.sqlite3` | DB | parsed, searchable rows (disposable) |

## The enhancement template pipeline (why the render cache exists)

When `parse_enhancements` meets a template call, it calls
`expand_enhancement_template()` (`catalog/enhancement_rules.py`), which decides
in this order:

1. **If a rule exists** for that template name (seeded from
   `enhancement_rule_seeds.py`, admin-editable in the DB), the rule's handler
   picks the canonical name and search value — and usually also composes the
   display text locally.
2. **If the wiki has already rendered** that exact call (the file cache in
   `wiki_snapshot/renders/`), the exact `display_text`, `canonical_name`,
   `value`, and `detail` from the render are attached — and they **win over**
   anything the rule composed, because the wiki's own output is ground truth.
3. If neither exists, a generic default handler guesses a value (usually
   poorly) — this is why the render cache matters, and why a fresh snapshot is
   always rendered before loading.

### Seeded rules

- **Enhancement bonus** → `{{Enhancement bonus|i|3}}` becomes two rows:
  "+3 Enhancement Bonus" and "Spellcasting Implement +9" (implement value =
  bonus × 3). Type letters: a/s/w = Armor/Shield/Weapon; i/ii/io/o/oi = Orb /
  Spellcasting implement variants.
- **SpellPower** → `{{SpellPower|Combustion|54}}` → name "Spell Power",
  value "Combustion 54", display "Combustion +54".
- **Spelllore** → `{{Spelllore|Fire|III}}` → "Fire Lore III"; numeric
  magnitudes render as "+N%".
- **HealingAmp** → `{{HealingAmp|8|h|Exceptional}}` → "Exceptional Healing
  Amplification +8" (type map h/r/n → Healing/Repair/Negative).
- **Named item (item-scope Mythic)** → auto-appends a Mythic row from the
  infobox's `mythic` field unless it's 0/no/false/n. Weapon/Armor get
  "+2 or +4", orb/shield/rune arm get both Weapon and Shield, quiver none,
  default `+1 or +3`. The slot-name mapping (Gloves → "Mythic Hands Boost…")
  lives in the wiki template, so its display text is always taken from the
  render cache, never composed.

Display-text composition is **only** done for variants verified against real
wiki renders (each seeded rule's config lists which forms are trusted);
anything unverified falls through to the wiki.

## Data models

- `Item` — name, wiki_title, wiki_page_id, wiki_revision_id, item_type,
  item_kind (e.g. "Named item"), minimum_level.
- `Enhancement` — unique wiki name (immutable) plus a blankable
  `display_name` override; `label` = display_name or name. Display names must
  not collide (case-insensitive) with any other enhancement's name or display
  name — enforced in the model's `clean()` and backed by a functional unique
  index on the effective label (`COALESCE(NULLIF(display_name, ''), name)`).
- `EnhancementVariant` — one row per distinct (enhancement, value, detail,
  display_text) of an enhancement, shared by every item that uses it;
  `magnitude` (nullable Float parsed from `value`) powers the minimum-value
  filter.
- `ItemEnhancement` — item + variant FK, tier (NULL = base line, 1/2/... =
  upgrade tier), raw_template. `enhancement` / `value` / `detail` /
  `display_text` / `magnitude` are properties proxying through the variant,
  so editing a variant updates every item using it.
- `EnhancementRule` — data-driven template rules (scope, handler, JSON config).
- The wiki-render cache is NOT a model — it lives in files under
  `wiki_snapshot/renders/` (see above).

## First-time setup (from a fresh machine)

> On this project machine the venv python is
> `& "D:\ddo_wiki_poc\venv\Scripts\python.exe" ...`. On a fresh machine,
> create your own venv and use its `python` below (or activate it first).

### 1. Environment

```powershell
python -m venv venv
.\venv\Scripts\Activate.ps1          # or call venv\Scripts\python.exe directly
pip install Django requests playwright
python -m playwright install chromium
```

`playwright` + a Chromium browser is required because ddowiki sits behind
**AWS WAF**: plain HTTP returns 202 challenge pages. The import command solves
the WAF token in headless Chromium and reuses it (see *Wiki access* below).

### 2. Create the database schema

```powershell
python manage.py migrate
```

This applies migrations `0001`–`0018` and creates `db.sqlite3` (SQLite, a
single file at the project root). `load_rules()` auto-seeds the default
`EnhancementRule` rows the first time parsing runs if the table is empty.

### 3. Populate data — the two offline sources of truth

Two things must exist before items can be imported:

1. **`wiki_snapshot/`** — raw wikitext for item pages
   (`manifest.json` + `pages/<pageid>.json`).
2. **`wiki_snapshot/renders/`** — the wiki's rendered output for each distinct
   enhancement template call (one JSON file per call).

Both require the wiki, so a full first-time setup does these in order:

```powershell
# (a) Crawl the wiki and capture raw wikitext to wiki_snapshot/
#     (full Item namespace: ~12,509 pages, ~5-6 min).
python manage.py import_wiki --snapshot

# (b) Ask the wiki to render every distinct enhancement template call,
#     caching the results (with raw_html) under wiki_snapshot/renders/.
#     The slow step — but calls are batched into ~168 requests.
python manage.py render_enhancements

# (c) Load the snapshot into the database. Pure local — no wiki calls.
#     --force reparses every page regardless of revision.
python manage.py import_wiki --load-snapshot --force
```

Order matters: `(b)` must run before `(c)` so the import can attach exact
display text / names from the render cache while parsing.

#### Recreating the database from scratch

The DB (`db.sqlite3`) is disposable — the snapshot AND the render cache both
live on disk, so a rebuild never touches the wiki:

```powershell
Stop the dev server
Remove-Item db.sqlite3                 # wipe the DB
python manage.py migrate              # recreate the schema
python manage.py seed_enhancement_rules   # reseed rules (empty table seeds itself too)
python manage.py import_wiki --load-snapshot --force
```

The render files under `wiki_snapshot/renders/` survive the wipe untouched,
so no re-fetch is needed.

#### Adding or fixing parsing logic later

- Parsing fix (only the extraction changed): the wiki output did not change —
  re-extract locally from the stored `raw_html`:

  ```powershell
  python manage.py render_enhancements --reparse   # instant, no wiki
  python manage.py import_wiki --load-snapshot --force
  ```

- Template rule change (editing `enhancement_rule_seeds.py` / a handler):
  re-run `--load-snapshot --force` to rebuild `ItemEnhancement` rows.

- Only if the **wiki's templates themselves** changed should you wipe the
  render cache and refetch:

  ```powershell
  python manage.py render_enhancements --clear   # full re-fetch, minutes
  ```

## Wiki access and WAF — read before touching the wiki

- The wiki is behind **AWS WAF**. `requests`/plain HTTP returns HTTP 202
  (challenge). Always go through the import command's `api_request()`.
- Flow (`import_wiki.py`): `solve_waf_token()` launches headless Chromium via
  Playwright, waits out the JS challenge, extracts the `aws-waf-token` cookie.
  Tokens are reused for 10 minutes and cached in `wiki_waf_token.json`
  (project root). On HTTP 202 the code re-solves and retries with backoff.
  A refresh at the start of a run is normal — the token file's expiry is
  unreliable, and a "fresh" cached token can still be rejected once.
- Pacing: `REQUEST_DELAY_SECONDS=1.0` + jitter `0.2` between requests to stay
  under the bot radar. A full crawl or a full render pass takes minutes.
- User-Agent: `DDOItemIndex/0.2 (personal project)` (MediaWiki policy).
- Query quirks: API titles carry the `Item:` prefix; titles starting with `+`
  decode to a space and 404 by title — query those by `pageids`. The
  `expandtemplates` API rejects newlines in `text` and over-long URLs (403) —
  batching caps at `BATCH_URL_LIMIT = 1900` and shrinks a rejected batch in
  half. Templates the wiki renders empty (e.g. `{{Sirocco|122}}`) are wiki
  behavior, not a bug; the affected items fall back to defaults.

## Management commands

| Command | What it does | Wiki? |
|---|---|---|
| `import_wiki --snapshot [DIR]` | Capture raw wikitext pages to a snapshot dir (default `wiki_snapshot/`) | yes (slow) |
| `import_wiki --load-snapshot [DIR]` | Parse the snapshot into the DB (`--force` reparses all pages) | no |
| `import_wiki --full` / `--page T` / `--limit N` / `--reset-sync` | Live crawl modes (DB path) | yes |
| `render_enhancements` | Cache every distinct enhancement template call's wiki render to `wiki_snapshot/renders/` (incl. `raw_html`), batched; backfills calls missing `raw_html` | yes, once per uncached call |
| `render_enhancements --reparse` | Re-extract name/display/value/detail from stored `raw_html` files | no |
| `render_enhancements --render-all` | Also fetch rule-composed calls (skipped by default) | yes |
| `render_enhancements --clear` | Wipe the render cache (forces full refetch next run) | — |
| `seed_enhancement_rules` | (Re)seed `EnhancementRule` rows from `enhancement_rule_seeds.py` | no |
| `clean_enhancements` | Rewrite existing `ItemEnhancement` values from stored raw templates (`--dry-run` to preview) | no |
| `test_browser` / `test_direct_api` | WAF debugging helpers (visible browser / expected-202 demo) | yes |

## Running the app

```powershell
python manage.py runserver 127.0.0.1:8090 --noreload
```

- Health check: `GET /?enhancement_options=1` → HTTP 200 with JSON.
- Admin (`/admin/`): superuser `admin` / `admin123` (dev). All models are
  registered; enhancement rules are editable at
  `/admin/catalog/enhancementrule/`.
- **Display names**: edit `display_name` in the admin's enhancement changelist
  (`/admin/catalog/enhancement/`) to override a wiki name everywhere it
  appears (dropdowns, item pages). The wiki `name` is read-only once the row
  exists. A display name can't collide with any other enhancement's name or
  display name (case-insensitive) — the admin will reject it. Dropdowns sort
  on the display name.
- Results are paginated 50/page, ordered by name.

## Key files

- `catalog/management/commands/import_wiki.py` — crawl/parse/load; the only
  wiki-touching code (WAF token + `api_request`).
- `catalog/management/commands/render_enhancements.py` — render cache (batched
  `expandtemplates` calls) + `--reparse` / `--render-all` / `--clear`.
- `catalog/enhancement_render_store.py` — loads/saves/clears the render files
  under `wiki_snapshot/renders/` and serves them from memory.
- `catalog/enhancement_rules.py`, `catalog/enhancement_rule_seeds.py` —
  data-driven template handlers and their seed config.
- `catalog/enhancement_renders.py` — `extract_rendered()`/`normalize_template_call()`
  (turning wiki HTML output into name/display/value/detail).
- `catalog/enhancement_values.py` — `parse_magnitude()`.
- `catalog/services.py`, `catalog/views.py` — filtering + search UI backend.
- `catalog/templates/catalog/item_search.html`,
  `catalog/static/catalog/js/item_search.js` — the frontend.

## Gotchas

- **PowerShell 5.1 writes UTF-16LE** when you redirect with `*>` or `>`.
  Read such captures as UTF-8 (or decode) before inspecting them, or mojibake
  will look like a logic bug.
- SQLite is a single file (`db.sqlite3`); stop the server before wiping it.
- The render cache lives in `wiki_snapshot/renders/`, not the DB — a DB wipe
  never requires a wiki re-fetch.
- `+` in wiki API titles decodes to a space → 404 by title; use `pageids`.
